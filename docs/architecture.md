2. エラーハンドリングの設計思想

エラーレスポンスをdetails(code/meta・code/message)に統一した理由：フロントでi18n対応やUI分岐をしやすくするため、という設計意図
normalizeApiErrorの責務：なぜフロントで正規化レイヤーを挟むのか（APIの形式変更に強くなる、コンポーネントがエラー形式を知らなくて済む）
concernのエラーハンドリング責務分離：どこで何を吸収しているか

3. データモデルの設計判断

concern / issue / roadmapを1:1で紐づけた理由：なぜ1:多ではないのか、将来的に変える余地はあるか

5. 技術選定の理由

Rails 8を選んだ理由：安定性、Active Record、
Next.js App Routerを選んだ理由：Pages Routerとの比較、SSR/CSRの使い分け
MUIを選んだ理由：Tailwindや他UIライブラリとの比較、アクセシビリティ、開発速度
SWR + Axiosの組み合わせ理由：React Queryとの比較、キャッシュ戦略、楽観的更新
RSpec / Jest + RTLの選定理由：minitestやVitestとの比較

ここは「完璧な答え」より「比較検討した痕跡」が大事

6. バリデーション設計

フロントとバックエンド両方でバリデーションする理由：UX（即時フィードバック）とセキュリティ（バイパス対策）の二重性
emailの小文字正規化をバリデーション前にする理由：一意性制約との整合
パスワード最小文字数を6→8に変えた理由：セキュリティ基準（NIST、OWASP）の参照

7. テスト戦略

何をテストして、何をテストしていないか：カバレッジ至上主義ではなく、リスクベースの判断
FactoryBot / Fakerの使い分け方針
Userモデルのバリデーションテストでdetailsを検証する理由：エラー種別の契約をテストで担保する意図
