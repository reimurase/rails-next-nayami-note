1. 認証・セッション設計
なぜCookie（セッション）方式を選んだか：JWTではなく。SameSite属性、HttpOnly、XSS耐性の観点で説明できるか
  ブラウザのみを対象とするWebアプリケーションのため、Cookieベースのセッション認証を採用した。
  1. Railsの標準機構に乗れる
  Rails は Cookie ベースのセッション管理を標準サポートしており、CSRF 対策・セッション固定攻撃対策などのセキュリティ機構が枯れた実装として提供されている。独自に JWT 認証基盤を組むよりもバグの混入リスクが低い。

  2. JWT を localStorage に保管する選択肢を避けられる
  SPA で JWT を扱う場合、保管場所として localStorage が候補になりがちだが、localStorage は JavaScript から自由に読めるため XSS 一発でトークンが盗まれる。これを避けて JWT を Cookie に入れるなら、結局セッション方式と同じ CSRF 対策が必要になり、JWT を採用する利点（ステートレス性）が薄れる。ブラウザのみを想定する本アプリでは、最初からセッション方式を選ぶ方が素直と判断した。

  3. XSSに対する防御層を持てる
  HttpOnly 属性を付与した Cookie は JavaScript からアクセスできないため、XSS 脆弱性が発生してもセッショントークン自体の窃取は防げる。これにより「セッションの永続的な乗っ取り（トークンを攻撃者のサーバへ送信されて後日悪用される）」を防止できる。
  ただし HttpOnly は万能ではない。XSS が成立した時点で、攻撃者は被害者のブラウザ上で正規ユーザーとして任意の API を叩けるため、「セッション継続中の不正操作」は防げない。あくまで XSS 対策の本丸は XSS そのものを防ぐこと（出力エスケープ・CSP等）であり、Cookie はその上での多層防御という位置づけで採用している。

  トレードオフと将来の拡張余地
  セッション方式はサーバ側に状態を持つため、将来スマホアプリやサードパーティ連携など Cookie が使えないクライアントを追加する場合は不向きになる。その場合は JWT を併用する設計を検討する。現時点ではブラウザ単一クライアントのため、この制約は問題にならない。

  ※ JWT はリクエストのたびに クライアントがトークンをHTTPヘッダに付けてサーバに送り、サーバ側は そのトークンの署名を検証するだけで認証が完了する 

  XSS 対策としては、Rails API モードで HTML を返さない構成にしていること、React のデフォルトの自動エスケープに乗っていることが主な防御である。dangerouslySetInnerHTML は使っていない。

CookieStore の制約と許容範囲：
  本実装は CookieStore を採用しているため、reset_session でログアウトしても、ログアウト前にコピーされた古いセッション Cookie はsecret_key_base がローテートされるまでサーバー側で無効化できない。
  HttpOnly + Secure + HTTPSで窃取自体を困難にすることを前提に、ポートフォリオ規模ではこの制約を許容する。
  ユーザー数が増えた段階で、サーバーサイドセッション（solid_cache_store によるキャッシュベース、または session_version カラムによる versioning）へ移行する余地がある。

user / session / me という3エンドポイント構成にした理由：RESTの設計思想とセッション管理の分離

  責務の分離
  usersはユーザーリソースの管理を担う。現時点ではPOST /users(サインアップ)のみ。ユーザーの作成という行為と、認証という行為は別の責務であるため、独立したりs−素として切り出している。
  sessionsは認証セッションの管理を担う。POST /session(ログイン)、DELETE /session(ログアウト)。「ログインする＝セッションというリソースを作る」「ログアウトする＝セッションを削除する」と捉えることで、RESTのCRUDに自然に対応する。
  meは認証済みユーザー自信の情報取得を担う。GET /meでフロント側が「今ログインしているのは誰か」を取得する。

なぜmeを独立させたか
  フロント側がユーザーIDを事前に知らなくて済む。 ページリロード時やアプリ初期化時に「自分は誰か」を取得する場面で、IDなしで叩ける。
  current_user を起点にすべて完結するため、IDの一致検証が不要になる

  将来の拡張余地
  認証方式を追加する場合（OAuth 等）、sessions 配下に新しいエンドポイントを追加する形で対応できる。users や me の責務には影響しない。この拡張のしやすさも分離の利点の一つである。

CSRF対策の仕組み：なぜSPAでもCSRFトークンが必要か、SameSite=Laxだけで足りない理由

  ※CSRFとは攻撃者が用意した悪意あるサイトを被害者が訪問した際に、被害者のブラウザから正規のAPIに対してリクエストを送らせる攻撃である。ブラウザはリクエスト先のドメインに応じてCookieを自動で添付するため、被害者がログイン中であれば、攻撃者のサイトから送られたリクエストにも認証済みのCookieが付いてしまう。結果として、被害者の意図しない操作（データの変更・削除等）が認証済みの状態で実行される。

  CSRFトークンは、正規のサイトからしか取得できない一意の値である。（SOPのおかげで）サーバはリクエストを受け取ったとき、このトークンが正しいかを検証する。
  攻撃者のサイトは被害者のブラウザにリクエストを送らせることはできるが、正規サイトからCSRFトークンを取得することはできない。これはブラウザのSame-Origin Policy（SOP）により、異なるオリジンからのレスポンスを読み取れないためである。トークンを持たないリクエストはサーバ側で拒否される。
  SameSite=Lax だけで済ませなかった理由
  SameSite=Lax は外部サイトからのPOSTリクエストにCookieを付けないため、基本的なCSRF防御として機能する。それでもCSRFトークンを併用した理由は以下の通り。

  SameSite 属性はブラウザ側の実装に依存する防御であり、サーバ側で検証できるCSRFトークンと組み合わせることで多層防御になる
  Railsの標準機構として提供されているため、導入コストがほぼない

  実装方針
  Railsの protect_from_forgery を利用し、独自実装は行っていない。フレームワークの枯れた実装に乗ることで、バグの混入リスクを下げている。

「2回目以降のログインで古いCSRFトークンを使って422になる不具合」の原因と解決:セッションリセット時のトークン再発行タイミング
  原因
  ログアウト時にサーバ側のセッションはリセットされ、CSRFトークンも新しくなる。しかしフロント側のJavaScript変数に保持していた古いCSRFトークンはそのまま残っていた。再ログイン時にこの古いトークンをヘッダに付けて送信したため、サーバ側の新しいトークンと一致せず422が返されていた。
  解決
  ログアウト・ログイン・サインアップの各タイミングで、フロント側のCSRFトークンも明示的にリセットし、サーバから新しいトークンを再取得するようにした。

サインアップ直後のセッション確立：なぜわざわざsession_idを作るのか
  1. UX上の配慮
  サインアップした直後に「ログインしてください」と再度メールアドレスとパスワードの入力を求めるのは、ユーザーにとって不要な手間である。サインアップした時点で本人確認は済んでいるので、そのままログイン済み状態に遷移させる方が自然である。
  2. 認証フローの一本化
  サインアップ時にもセッションを作ることで、サインアップ・ログインどちらの経路でも同じ認証フローに合流する。フロント側で「サインアップ後の未認証状態」を別途管理する必要がなくなる。
  補足：メール確認ステップを挟まない判断について
  本来、メールアドレスの実在確認のためにサインアップ後に確認メールを送る設計が望ましい。確認を省略した場合、メールアドレスの誤入力でパスワードリセットが不可能になるリスクがある。今回はポートフォリオとしてUXの手軽さと実装速度を優先して省略しているが、実務では必須の機能である。

2. エラーハンドリングの設計思想

エラーレスポンスをdetails(code/meta・code/message)に統一した理由：フロントでi18n対応やUI分岐をしやすくするため、という設計意図
  バックエンドからのエラーレスポンスの形式を統一している。すべてのエラーは以下の構造で返す。
  {
    "details": [
      { "code": "too_short", "meta": { "count": 8 } },
      { "code": "invalid_format", "message": "メールアドレスの形式が正しくありません" }
    ]
  }
  統一した理由
  エラーの形式がエンドポイントごとにバラバラだと、フロント側で「このAPIはどういう形式でエラーを返すか」を個別に知る必要がある。形式を統一することで、フロント側のエラー処理を一箇所にまとめられる。
  code を含める理由
  エラーメッセージの文字列（"パスワードが短すぎます"）だけを返すと、フロント側でエラーの種類を判定するのに文字列比較が必要になる。文言変更やi18n対応のたびにフロント側の分岐も修正が必要になり、壊れやすい。code（"too_short" 等）を返すことで、フロント側は文言に依存せずにエラーの種類を判定できる。
  meta を含める理由
  エラーの補足情報（最小文字数など）をフロント側に渡すため。フロント側で「8文字以上で入力してください」のようなメッセージを組み立てる際に、この値がないとフロント側にもハードコードすることになり、バックエンドとの二重管理になる。
normalizeApiErrorの責務：なぜフロントで正規化レイヤーを挟むのか
  1. APIの形式変更に強くなる。 バックエンドのエラーレスポンス構造が変わった場合、normalizeApiError だけを修正すれば済む。この関数がなければ、エラーを扱うすべてのコンポーネントを修正する必要がある。
  2. コンポーネントがAPIのエラー形式を知らなくて済む。 各コンポーネントは正規化後の統一された形式だけを扱えばよい。「APIがどういう構造でエラーを返すか」という知識が個々のコンポーネントに散らばらない。
  つまり、APIのエラー形式とコンポーネントのエラー表示の間に 変換層を一枚挟むことで、双方の変更が互いに影響しなくなる。

concernのエラーハンドリング責務分離：どこで何を吸収しているか
  concernのバリデーションエラー処理は、concernValidation という関数に切り出している。
  分離の構造

  concernValidation: 必須チェック・文字数チェックなどのバリデーションロジックを持つ。入力値を受け取り、エラーがあればエラー情報を返す。
  コンポーネント: concernValidation を呼び出し、返ってきたエラーを表示するだけ。バリデーションの具体的なルールは知らない。

  なぜ分離したか
  バリデーションロジックがコンポーネントの中に直接書かれていると、同じバリデーションを別の画面でも使いたいときにコードが重複する。また、コンポーネントが「UIの表示」と「入力値の検証」という2つの責務を持つことになり、どちらかを変更したいときにもう一方に影響するリスクがある。
  関数として切り出すことで、バリデーションルールの変更はその関数だけ、表示の変更はコンポーネントだけで済む。

3. データモデルの設計判断

concern / issue / roadmapを1:1で紐づけた理由：なぜ1:多ではないのか、将来的に変える余地はあるか
  本アプリは「悩みを書いて整理し、忘れる」ことを目的としている。3つのリソースは、悩みの処理を段階的に進めるための構造である。

  concern: 悩みの言語化。きっかけ・感情・状況をとにかく書き出す場所。整理や解決策を考えることは一旦置いて、状況の羅列に集中する。
  issue: 悩みの整理。concernを見ながら、具体的な問題を抽出し、優先順位をつけて整理する場所。
  roadmap: 解決への道筋。マイルストーンとなる事柄を書き出し、目標までの道筋を見える化する場所。

1:1にした理由
  1つのconcernに複数のissueを紐づけられるようにすると、2つの問題が生じる。
  1つ目は、悩みが構造的に複雑化することである。1つの悩みに対して複数のissueが並ぶと、それ自体が整理の対象になり、「悩みを整理するために悩みを管理する」という本末転倒が起きる。
  2つ目は、concernが増えてきたときに「このissueはどのconcernに紐づけたら良いのか」という関連付け探しが発生することである。これも悩みの解消ではなく管理に時間を取られる要因になる。
  1:1にすることで、concern → issue → roadmap という流れが常に一本道になり、ユーザーは管理ではなく悩みの処理に集中できる。
  将来の拡張余地
  現在はconcernを起点にissue・roadmapを作成する流れだが、将来的にはissueやroadmapを起点にconcernと関連付ける導線も検討している。1:1の関係自体は維持する方針である。  

アーカイブを論理削除（archived_at）にした理由：物理削除との比較、復元要件、パフォーマンス影響
  concernの削除は物理削除だけでなく、archived_at カラムによる論理削除（アーカイブ）も採用している。
  物理削除にしなかった理由
  本アプリのコンセプトは「書いて忘れる」であり、悩みを手放すことを促す設計になっている。しかし、書いたものが完全に消えてしまうことに対してユーザーは不安を感じる。アーカイブという形で一覧からは消えるが、データ自体は残っている状態にすることで、「いつでも見返せる」という安心感を持ったまま手放すことができる。
  
UIラベル「ライブラリ」とAPIパスarchivedのズレ：ユーザー向け言語と内部表現を分ける思想
  ユーザー向けのUIでは「ライブラリ」と表示し、API上は archived としている。ユーザーにとって「アーカイブ」は「データ置き場」のニュアンスがあるが、実際には自分が悩んだ軌跡であり、振り返りの価値がある。「ライブラリ」という言葉で、自分の過去の記録を蓄積・閲覧する場所というニュアンスを持たせている。API側はデータの状態を正確に表す archived をそのまま使い、ユーザー向け表現と内部表現を分けている。

自動アーカイブ（concernのみ実装）
作成から1週間で自動的にアーカイブされる。延長はない。これもアプリのコンセプトに基づく判断で、悩みをいつまでも一覧に残しておくと、繰り返し目に入ることで手放すことの妨げになる。期限を区切ることで「書いたら忘れる」を仕組みとして後押ししている。
また、なやみは移ろいやすいため、時間がへるごとにその価値やニュアンスが変化していくため、一度リセットすることで再定義を促す意図も含まれる

自動アーカイブ機能の発火タイミング：どこで判定しているか
  自動アーカイブは、concernの一覧取得APIが呼ばれたタイミングで発火する。一覧を返す前に、作成から1週間を超えたconcernをアーカイブし、その後で残ったアクティブなconcernを返す。
  この方式を選んだ理由
  シンプルだからである。バックグラウンドジョブ（cron等）で定期実行する方法もあるが、ジョブの管理・監視・障害対応など運用面の複雑さが増す。一覧取得時に処理することで、追加のインフラなしでアーカイブ機能が実現できる。
  トレードオフ
  一覧を開くたびにアーカイブ対象の検索と更新が走るため、効率的ではない。アーカイブ対象がなくても毎回クエリが発生する。データ量が増えた場合、一覧の表示速度に影響する可能性がある。
  将来の改善余地
  ユーザー数やデータ量が増えた場合は、バックグラウンドジョブでの定期実行に切り替え、ログイン時にアーカイブされたことを通知するだけにする方法が考えられる。現時点ではポートフォリオの規模で問題にならないため、シンプルさを優先している。

4. レート制限

## レート制限の現状と課題

### 現状
- ログイン・サインアップ・パスワードリセット・ゲストログインに IP 単位のレート制限を実装
- パスワードリセット・ログインにはメールアドレス単位のレート制限を追加

### 課題
- Render が Cloudflare を経由するため、`trusted_proxies` に Cloudflare の IP レンジが未設定の状態では `request.remote_ip` が実クライアント IP ではなく変動する Cloudflare 中継 IP を返す
- その結果、IP 単位のレート制限は現状機能していない

### 対応方針
- IP 非依存のメールアドレス単位の制限を主防御層として位置づけ
- 根本解決は `trusted_proxies` への Cloudflare IP レンジ登録、または AWS 移行（ECS Fargate + VPC 構成で実 IP が安定取得可能）を今後の課題として認識

ログイン・サインアップに限定してかけた理由：ブルートフォース対策、全APIにかけない理由
  ログインとサインアップのエンドポイントにのみ、IPベースのレート制限を設けている。
  制限の設定

  ログイン: 同一IPから3分間に10回まで
  サインアップ: 同一IPから10分間に5回まで

  サインアップの方を厳しくしているのは、正規ユーザーがサインアップを短時間に何度も試みることは通常ないためである。ログインはパスワードの打ち間違いなどで複数回試行する場面があるため、やや緩めに設定している。

なぜこの2つだけにかけたか
  レート制限の目的はブルートフォース攻撃（パスワードの総当たり）への対策である。パスワード認証を伴うエンドポイントが攻撃対象になるため、ログインとサインアップに限定した。他のAPIはセッション認証済みでないとアクセスできないため、ブルートフォースの対象にならない。
  全APIにかけなかった理由
  リクエスト量の制御（DDoS対策等）が目的ではないため、全APIにかける必要がないと判断した。DDoS対策が必要になる規模であれば、アプリケーション層ではなくインフラ層（CDN、ロードバランサー等）で対処するのが適切である。
  実装方針
  Rails 8の標準機能である rate_limit を使用している。独自実装ではなくフレームワークの機能に乗ることで、導入コストとバグのリスクを下げている。制限に引っかかった場合はエラーメッセージを返し、制限時間経過後に自動で解除される。

ゲストログインには厳しめのレート制限を追加
  誰でも何度でも叩けるため、Dosの経路になる。それを軽減するために、厳し目のレート制限を設定。

  将来の拡張余地
  DBの肥大化を対策するためにjobを利用して、未使用ゲストの定期削除を実装する。
  # 例: 30日間ログインしてないゲストを削除
  User.where(guest: true).where("updated_at < ?", 30.days.ago).find_each(&:destroy)

5. 技術選定の理由

Rails 8を選んだ理由：安定性、Active Record、
  バックエンドにはRailsを採用した。他のフレームワークとの比較検討はしておらず、以下の理由からRailsを前提として学習を進めた。

  Web系の未経験向け教材が豊富で、独学で体系的に学びやすい
  現在も求人数が多く、転職先の選択肢が広い
  Active RecordによるDB操作、認証、セッション管理など、Webアプリに必要な機能が標準で揃っており、少人数（一人）で開発を進めやすい

なぜNext.jsか
  素のReactではなく、フレームワークとしてのサポート（ルーティング、ビルド設定、ファイルベースのルーティング等）を受けるためにNext.jsを採用した。素のReactではこれらを自分で構築・管理する必要があり、一人での開発では負担になる。

なぜApp Routerか
  App Routerはディレクトリ構成でルーティングとレイアウトを明確に分離できる点を評価して採用した。Pages Routerでも開発は可能だが、App Routerの方がNext.jsの今後の主流であり、新機能もApp Router向けに提供されている。

SSRではなくCSRで実装している理由
  サーバーコンポーネントはNext.jsのサーバー上で実行されるため、ブラウザが保持しているCookieはRails APIへのリクエストに自動で付与されない。認証が必要なAPIを叩くと401になるため、現時点ではクライアントコンポーネント + SWRでのデータ取得に寄せている。解決策として同一オリジン化（リバースプロキシでフロントとAPIを同じオリジンに配置する）を検討しているが、実装初期段階ではインフラ構成より機能実装を優先し、保留にしている。

MUIを選んだ理由：Tailwindや他UIライブラリとの比較、アクセシビリティ、開発速度
  採用理由
  一人での開発でデザインに時間をかけられないため、コンポーネントをそのまま使えば一定の見た目と操作性が保証されるMUIを選んだ。ボタン、フォーム、ダイアログなどの基本的なUIパーツが揃っており、デザインを一から考える必要がない。

Tailwindを選ばなかった理由
  Tailwindはユーティリティクラスを組み合わせて自分でデザインを組み立てるアプローチである。自由度は高いが、デザインの判断を自分でする場面が多くなる。デザインスキルに時間を割くよりも、機能実装を優先したかったためMUIの方が合っていた。
  UIの開発コストを下げるため。ある程度デザインが決まっているMUIを採用

SWR + Axiosの組み合わせ理由：React Queryとの比較、キャッシュ戦略、楽観的更新
  SWR
  データ取得時のローディング・エラー・データの状態管理を簡潔に書くために導入した。SWRを使わない場合、useEffect + useState でこれらの状態を自分で管理するコードを書く必要がある。SWRはこれを数行で実現でき、加えてキャッシュや自動再取得の機能も得られる。
  Axios
  ブラウザ標準の fetch でもAPI通信は可能だが、リクエスト・レスポンスのインターセプター（共通処理の挟み込み）やエラーハンドリングなど、fetch では自分で実装する必要がある機能が標準で備わっている。アプリの規模が大きくなることを見越して、最初からAxiosを採用した。

RSpec / Jest + RTLの選定理由：minitestやVitestとの比較
  RSpec
  Railsのテストフレームワークとして、標準のMinitestではなくRSpecを採用した。Railsの現場で広く使われているデファクトスタンダードであり、求人でもRSpecの経験が求められることが多いため、実務を見据えて選択した。

  Jest + React Testing Library（RTL）
  Next.js / Reactのテスト環境として導入した。Jestはテストランナーとして、RTLはコンポーネントのテストを書くためのライブラリとして、React公式が推奨する組み合わせである。RTLは「ユーザーが実際に操作する視点」でテストを書く設計思想を持っており、実装の内部構造に依存しないテストが書ける。

ここは「完璧な答え」より「比較検討した痕跡」が大事

6. バリデーション設計

フロントとバックエンド両方でバリデーションする理由：UX（即時フィードバック）とセキュリティ（バイパス対策）の二重性
  フロントとバックエンドの両方でバリデーションを実装している。目的が異なるためである。

  フロント側のバリデーション
  ユーザーに即時フィードバックを返すためである。入力のたびにエラーを表示することで、送信前に誤りに気づける。UXの向上が目的であり、セキュリティ上の保証にはならない。

  バックエンド側のバリデーション
  データの整合性を保証するためである。フロント側のバリデーションはブラウザの開発者ツールやAPIの直接呼び出しでバイパスできるため、最終的な防御はバックエンド側が担う。フロントで誤って通過した入力も、バックエンドで必ずブロックされる。

emailの小文字正規化をバリデーション前にする理由：一意性制約との整合
  データの一貫性を保つためである。MySQLのデフォルト設定では大文字小文字を区別せずに一意性を判定するため、重複登録自体は正規化しなくても防げる。しかし正規化しないと、保存される文字列の表記がユーザーごとにバラバラになる。保存前に小文字へ統一することで、DB内のデータ形式が常に揃い、メール送信やログ出力など他の処理で参照する際にも一貫した値を使える。

パスワード最小文字数を6→8に変えた理由：セキュリティ基準（NIST、OWASP）の参照
  NIST（米国国立標準技術研究所）やOWASPのガイドラインを参照した。多要素認証がない場合の推奨最小文字数は16文字だが、ポートフォリオアプリとしてのUXを考慮し、多要素認証ありの場合の最小文字数である8文字を採用した。
  トレードオフ
  セキュリティ基準としては16文字が望ましいが、ポートフォリオアプリで16文字を要求するとユーザーの利便性を大きく損なう。8文字は妥協点であり、実務ではアプリの性質やリスクに応じて判断が変わる部分である。

7. テスト戦略

何をテストして、何をテストしていないか：カバレッジ至上主義ではなく、リスクベースの判断
  バックエンド

  モデルのバリデーションテスト: 正常系・異常系を網羅し、エラー種別（details）まで検証している
  リクエストテスト: APIの全体的な動作（ステータスコード、認証の要否など）を検証している
  テストしていない部分: エラーレスポンスの形式（code/metaの構造）までは検証していない。レスポンス形式を統一する設計にしているが、それをテストで担保するところまでは実装が追いついていない

  フロントエンド

  表示系テスト: 一覧・詳細画面やエラー表示など、主要な画面の表示を検証している
  関数の呼び出しテスト: イベントハンドラが正しい関数を呼び出しているかを検証している
  テストしていない部分: ユニットテスト（個々の関数の入出力検証）は未実施。また、開発途中でUIの仕様が頻繁に変わるため、表示系のテストは途中から最低限に抑え、関数の呼び出しテストを優先した。仕様が固まった段階で表示系テストを充実させる方針である

  判断の基準
  実装優先の方針で、すべてを網羅するのではなく書ける範囲でテストを追加してきた。バリデーションはデータの整合性に直結するため優先的にテストし、フロントの表示系テストは仕様が頻繁に変わる段階ではテストの維持コストが高いため、最低限に抑えた。

Userモデルのバリデーションテストでdetailsを検証する理由：エラー種別の契約をテストで担保する意図
  バリデーションテストでは、エラーが発生すること自体だけでなく、エラーの種別（details）まで検証している。
  理由
  エラーが返ること自体の確認だけでは、意図したバリデーションルールで弾かれているのか、別のバリデーションでたまたま弾かれているのか区別できない。例えば、パスワードが短すぎるテストで「エラーが1件ある」とだけ検証すると、文字数チェックではなく空文字チェックで引っかかっていても通ってしまう。
  detailsのcodeまで検証することで、「意図したバリデーションルールが正しく機能しているか」を確認できる。

低優先

CI/CD設定、Rubocop、ESLint、Prettierの詳細ルール
  GitHub Actionsでバックエンド（RSpec、Rubocop）とフロントエンド（Jest、ESLint）のテスト・静的解析をプッシュ時に自動実行している。手動でのチェック漏れを防ぎ、mainブランチに壊れたコードが入ることを防止する目的である。

  コードの書き方をチーム（将来的な想定を含む）で統一するために導入している。一人での開発でも、時間が経つと自分自身の書き方にブレが出るため、ルールとして固定する意味がある。RubocopはRubyの、ESLintはTypeScriptの静的解析を担い、PrettierはコードフォーマットをESLintの責務から分離して担当している。

i18n導入の手順
  Railsのバリデーションエラーメッセージを日本語化するために導入した。当初はRailsが返すエラーメッセージをそのままフロントに表示する方針だったが、その後エラーレスポンスを code/meta 形式に統一し、フロント側でメッセージを組み立てる方式に変更した。そのため、現時点ではi18nの日本語メッセージをフロントに直接表示する場面はなくなっている。
  ただし、Rails内部のログやデバッグ時のエラー表示が日本語になる点では引き続き役立っている。

ヘルスチェックAPIの内容
  アプリケーションが正常に起動しているかを確認するためのエンドポイントである。アクセスするとJSONレスポンスを返す。デプロイ後の動作確認や、Renderの死活監視で使用する。

Renderを選んだ理由（ただし「なぜVercel/Herokuではないか」は一応用意）
  学習教材でRenderが使われていたため、そのまま採用した。HerokuやVercelとの詳細な比較検討はしていない。Renderは無料プランでRailsアプリをデプロイでき、ポートフォリオの公開環境として十分と判断した。
